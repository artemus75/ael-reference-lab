# Management GitOps Reference

## Purpose

This reference describes the GitOps control path used to reconcile the Management Plane from Git.

The objective is not merely to install Flux. The architectural concern is to establish a clear desired-state authority, a reconciliation mechanism, and an explicit boundary between repository state and runtime state.

The reference implementation uses Flux to reconcile the Management Plane from this repository.

## Architecture

The control path is:

```text
Git repository
      ↓
GitRepository / flux-system
      ↓
clusters/management
      ↓
Flux Kustomization
      ↓
platform/management
      ↓
Management Plane desired state
```

The responsibilities are deliberately separated:

```text
Git
  desired-state authority

Flux
  reconciliation mechanism

Kubernetes API
  execution target
```

GitOps does not make the runtime itself authoritative. Runtime changes that are not represented in Git can be reverted by reconciliation.

## Repository Structure

The reference implementation is split into two layers:

```text
clusters/management/
├── kustomization.yaml
├── platform.yaml
└── flux-system/
    ├── kustomization.yaml
    ├── gotk-components.yaml
    └── gotk-sync.yaml

platform/management/
└── kustomization.yaml
```

`clusters/management/` defines the cluster-level reconciliation entry point.

`platform/management/` is the extension point for Management Plane platform resources.

This separation keeps Flux bootstrap and platform desired state distinct.

## Flux Bootstrap

The Flux bootstrap resources are stored under:

```text
clusters/management/flux-system/
```

`gotk-components.yaml` is generated by Flux and represents the versioned controller installation used by this reference.

It was generated for Flux v2.9.5 with:

- `source-controller`
- `kustomize-controller`
- `helm-controller`

The generated manifest should not be manually edited. A Flux version or component change should instead be treated as an explicit bootstrap change and regenerate the artifact using Flux tooling.

## Git Source

The public reference points to:

```text
ssh://git@github.com/artemus75/ael-reference-lab.git
```

This makes the published repository internally consistent: the Flux source and the referenced reconciliation paths exist in the same repository.

For an actual deployment, use the repository that owns your desired state, for example:

```text
ssh://git@github.com/<your-account>/<your-repository>.git
```

The deployment repository must contain the corresponding paths expected by the Flux Kustomizations.

## Authentication Boundary

The `GitRepository` references:

```yaml
secretRef:
  name: flux-system
```

The referenced Secret contains repository authentication material and is intentionally not stored in this repository.

The public manifests define the dependency on that Secret, not its credentials.

A deployment must provision suitable Git authentication independently.

## Reconciliation Layers

The first reconciliation layer is the Flux system itself:

```text
GitRepository: flux-system
        ↓
Kustomization: flux-system
        ↓
./clusters/management
```

The cluster configuration then declares the Management Plane platform reconciliation:

```text
Kustomization: platform-management
        ↓
./platform/management
```

This creates a deliberate hierarchy:

```text
Flux bootstrap
      ↓
cluster reconciliation
      ↓
platform reconciliation
```

## Empty Platform Extension Point

The current public reference contains:

```yaml
resources: []
```

in:

```text
platform/management/kustomization.yaml
```

This is intentional.

The public repository demonstrates the Management Plane GitOps control structure without publishing private Management Plane workloads or environment-specific resources.

Consumers can add their own platform resources beneath this path and include them in the Kustomization.

An empty resource list therefore represents an extension boundary, not an incomplete Flux bootstrap.

## Reconciliation Behavior

The Flux Kustomizations use:

```yaml
prune: true
```

This means resources previously reconciled by Flux can be removed from the cluster when they are removed from the declared desired state.

That behavior is part of the lifecycle contract and should be considered when changing repository structure or resource ownership.

Reconciliation intervals are also explicit in the manifests rather than treated as runtime defaults.

## Privilege Boundary

The generated Flux controller manifest grants significant Kubernetes permissions to the reconciliation controllers, including cluster-level privileges required to manage platform resources.

This is an architectural trust boundary.

A repository change accepted by Flux can therefore result in privileged changes to the cluster.

Repository access, branch protection, review policy, Git credentials, and Flux controller permissions should be treated as part of the Management Plane security model rather than as independent implementation details.

The permissions in the generated reference manifest reflect the selected Flux bootstrap configuration. They are not presented as a universal least-privilege model.

## Bootstrap Versus Steady State

GitOps introduces an important bootstrap dependency:

```text
Flux must exist
before
Flux can reconcile Flux-managed desired state
```

Initial bootstrap therefore remains distinct from steady-state reconciliation.

Once Flux is operational, the repository becomes the source from which the declared Management Plane state is continuously reconciled.

This distinction matters during disaster recovery: restoring Kubernetes alone does not prove that GitOps reconciliation has recovered.

## Recovery Validation

A Management Plane recovery should validate the complete control path:

```text
Kubernetes API available
        ↓
Flux controllers available
        ↓
GitRepository ready
        ↓
Flux Kustomizations ready
        ↓
platform-management ready
        ↓
declared platform state converged
```

Useful validation commands include:

```bash
kubectl get nodes
flux get sources git -A
flux get kustomizations -A
flux get all -A
```

A healthy Kubernetes node alone is insufficient evidence that the GitOps control path has recovered.

## Public Reference Boundary

This repository publishes the reusable GitOps control structure.

It does not publish:

- private repository credentials
- deploy keys or SSH private keys
- private Management Plane workloads
- environment-specific cluster identities
- runtime evidence
- recovery evidence from the private engineering environment

The public manifests are a reference implementation. Validation evidence from a private environment does not automatically transfer to another deployment.

## Adaptation Checklist

Before using this reference in another environment:

1. Fork or copy the repository into the desired-state repository.
2. Change the `GitRepository` URL to that repository.
3. Provision repository authentication for the `flux-system` Secret.
4. Review the generated Flux version and controller set.
5. Review Flux RBAC against the intended trust model.
6. Confirm the reconciliation paths exist.
7. Add Management Plane resources under `platform/management/`.
8. Review `prune: true` against the resource ownership model.
9. Bootstrap Flux using the intended operational procedure.
10. Validate source, Kustomization, and platform reconciliation independently.

## Evidence Boundary

The structure published here is derived from the Management Plane GitOps implementation used in the engineering environment.

The public repository contains the reusable control structure, not private runtime evidence.

A successful deployment of this reference therefore requires its own validation of bootstrap, authentication, reconciliation, convergence, and recovery behavior.
